# n8n 2.4.0 Compatibility Notes

## Version pin

The repository pins:

```json
"n8n": "2.4.0"
```

The runtime scripts reject a different detected n8n version. This prevents workflow JSON from being silently built or tested against another version.

## Node.js range

Package metadata for `n8n@2.4.0` declares Node.js `>=20.19 <=24.x`. The environment validator enforces an equivalent range: at least 20.19 and below 25.

## Package alignment

The `n8n@2.4.0` package declares aligned core packages including:

- `n8n-core@2.4.0`
- `n8n-nodes-base@2.4.0`
- `@n8n/n8n-nodes-langchain@2.4.0`

Workflow exports must be produced or verified against the installed local package, not copied from a newer n8n instance.

## Runtime settings used in Phase 1

- `N8N_HOST=localhost`
- `N8N_LISTEN_ADDRESS=127.0.0.1`
- `N8N_PORT=5678`
- `N8N_PROTOCOL=http`
- `N8N_USER_FOLDER=<project>\.runtime\n8n-user`
- `WEBHOOK_URL=<active ngrok HTTPS URL>` in the child process
- `N8N_PROXY_HOPS=1`

Binding n8n to `127.0.0.1` prevents direct LAN exposure. ngrok is the controlled public ingress.

## Node compatibility inventory for future workflows

Current public documentation confirms the relevant built-in node families exist in n8n, but exact node `typeVersion`, operation names and parameter structures must be inspected from the installed `2.4.0` editor/export before each workflow is generated.

Planned node families requiring exact verification:

| Node family | Planned use | Verification required before export |
|---|---|---|
| Webhook / Respond to Webhook | Portal and authenticated operations | route, HTTP method, response mode, binary handling |
| Schedule Trigger | polling, dispatcher, monitoring | schedule parameter format and timezone |
| Google Sheets | Forms response intake and dashboard | trigger availability, append/read/update operations |
| Google Drive | uploaded marks and generated documents | search, copy, download, upload and folder operations |
| Google Docs | transcript population | available actions and table limitations |
| Gmail | official notification sender | send operation and attachment input format |
| Supabase | simple operations where safe | credentials and operation coverage |
| Postgres | controlled database access if required | credentials, query parameters and transaction boundary |
| HTTP Request | public RPC/Auth/Docs API fallback | auth, JSON body and retry settings |
| Extract From File | CSV/XLSX marks import | supported formats and binary property |
| Edit Fields, IF, Switch, Merge, Split Out, Loop Over Items | data shaping and flow control | exact type versions and branch output behavior |
| Error Trigger | root incident handler | event payload fields in 2.4.0 |

## Security and maintenance boundary

Version 2.4.0 is retained only because it is an explicit compatibility requirement. It must not be silently upgraded, but it must also not be assumed safe indefinitely. Before a real institutional pilot, perform a current security review and decide whether the compatibility target must be revised. Version notifications remain enabled.

## No workflow JSON yet

Phase 1 deliberately creates no workflow export. The first export is blocked until:

1. the local `2.4.0` instance runs;
2. node inventory evidence is captured from that instance;
3. Phase 2 database contracts are applied and tested;
4. Phase 3 Google/Auth setup is verified.
